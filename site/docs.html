1 · Install & upgrade

One line

# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/muthuishere/sec/main/install.sh | sh

# Windows (cmd, no PowerShell)
curl.exe -fsSL https://raw.githubusercontent.com/muthuishere/sec/main/install.cmd -o "%TEMP%\sec-install.cmd" && "%TEMP%\sec-install.cmd"

What the installers do

  • Install into $SEC_BIN_DIR, default ~/.local/bin (%USERPROFILE%\.local\bin on Windows). Never root or Administrator.
  • If go is on PATH (and SEC_NO_GO is unset) they run go install github.com/muthuishere/sec/cmd/sec@latest; otherwise they download the latest release binary for your OS/arch.
  • PATH: install.sh appends export PATH=… # sec once to ~/.zshrc, ~/.bashrc or ~/.profile (by $SHELL); install.cmd adds the folder to your user PATH with setx. Open a new shell afterwards.
  • Finally run sec skill install (skill into ~/.claude/skills and ~/.agents/skills, plus harness deny rules) and print the version.

Bare binary

Release binaries are built for linux, darwin and windows on amd64 and arm64, named sec_<os>_<arch> (.exe on Windows) at https://github.com/muthuishere/sec/releases/latest/download/. Drop one on PATH and run anything: the first run installs the agent skill into every skill root that has none and adds the deny rules, then leaves a skill-installed stamp in the sec home so it happens once — a skill you later remove stays removed.

From source

git clone https://github.com/muthuishere/sec && cd sec && task install
sec init

Upgrade

Re-run the one-liner. After that, every sec run keeps the installed skill current: a skill folder sec wrote that differs from the one built into the binary is rewritten in place. Symlinked skills (a dev checkout) and folders holding other files are left alone. To upgrade sec on another machine use sec remote upgrade.

Windows notes

  • The installer is plain cmd + curl.exe (built into Windows 10+); it picks arm64 when PROCESSOR_ARCHITECTURE is ARM64, else amd64.
  • The identity defaults to the Windows credential store (keyring), like macOS.
  • sec sync --install / sec remote install detect a Windows far end via PowerShell and install into %LOCALAPPDATA%\Programs\sec — no Administrator.
  • Home is %USERPROFILE%\.config\sec unless SEC_HOME (or XDG_CONFIG_HOME) is set.

2 · Quickstart

sec init                                   # identity + empty vault
sec set OPENAI_API_KEY                     # masked prompt
sec import .env                            # or bring a whole .env in
sec run OPENAI_API_KEY -- python app.py    # as an env var, output scrubbed
sec exec -- curl -H 'Authorization: Bearer {{GH_TOKEN}}' https://api.github.com/user
sec ok                                     # anything missing / stale?

sec init

Create the age identity and an empty vault.

sec init [--backend keyring|file] [--import-identity FILE]

  --backend keyring|file      where to keep the key (default: keyring if the OS store answers)
  --import-identity FILE      adopt an existing age identity instead of generating one

sec init --backend file          # servers, containers, CI

3 · Concepts

  • Vault — ~/.config/sec/vault/NAME.age (age X25519, filippo.io/age) plus NAME.json metadata. Ciphertext and names only. Home is ~/.config/sec ($XDG_CONFIG_HOME/sec if set); override with SEC_HOME (handy for a throwaway vault in a test).
  • Identity — SEC_IDENTITY env > OS keyring > identity.txt (0400). macOS and Windows default to the keyring; Linux, BSD, containers and CI default to the file, because a server has no Secret Service and a desktop one is DBus that can block on an unlock prompt nobody will answer in cron. See sec identity.
  • Owner vs agent — a TTY on stdin, or SEC_OWNER=1, is the owner. Agent harnesses run with a piped stdin, so they never are. What needs the owner is in the owner-only matrix.
  • Redaction — exec, run and sh scrub each value plus its base64 (with and without trailing newline), hex, URL-encoded and JSON-escaped forms from stdout and stderr. Matching is newline-tolerant — the stream is also searched with \r and \n removed, so a value wrapped across lines (xxd -p, GNU base64, fold) is still caught. The tail is held back briefly so a match cannot slip through the seam; output can lag a few hundred bytes behind.
  • Placement ledger — push, render, import, gen --env and push record where a value went; rotate, set --place and ok replay them.
  • Audit — ~/.config/sec/audit.ndjson: action, names, agent, cwd, template. Never values.

Projects, environments, scoped names

A name may be scoped — project:NAME, project@env:NAME or @env:NAME (e.g. reqsume@production:POSTGRES_PASSWORD) — anywhere a name goes, including inside {{…}}. Bare names resolve in the current context: project@env, then project, then global. Precedence: --project/--env on any command and explicit scoped names beat SEC_PROJECT/SEC_ENV, which beat the repo's .sec.toml, which beats sec use.

A repo names its project in .sec.toml at its root — no secrets in it, so commit it and the whole team resolves the same project:

project = "billing"
envs = ["dev", "staging", "production"]
default_env = "dev"

Anywhere in that repo bare names resolve in project@env, then project, then global — no flag, no sec use. The env is default_env until you switch: sec use staging inside the repo (kept on your machine for that repo only, never in the file; sec use --unset goes back to the default; sec use shows it). Only envs listed in envs are accepted. Step out of the repo and its context is gone. sec import .env [--env dev] writes the file when there is none, named after the repo root or folder (My App → my-app) or the --project NAME you give. A legacy .sec file still works. $HOME and / never count as a repo. With sec run a scoped name arrives as its plain NAME env var.

4 · Use — run work with secrets, never seeing them

sec exec

Run a command or script with {{NAME}} placeholders filled; output scrubbed. The verb for anything that takes a credential as an argument or inside a body.

sec exec -- CMD ARGS with {{NAME}}
sec exec -f SCRIPT [-- args]

  -f FILE                 script/template to render and execute (args after -- go to it)
  --allow-output-only     owner-only: permit echo/cat/env style commands

sec exec -- curl -H 'Authorization: Bearer {{GH_TOKEN}}' https://api.github.com/user
sec exec -- psql postgres://app:{{reqsume@production:POSTGRES_PASSWORD}}@db/app

sec run

Run a command with secrets injected as environment variables; output scrubbed.

sec run NAME[,NAME2][=ENVVAR] -- CMD ARGS

sec run OPENAI_API_KEY -- python app.py
sec run DB_PW=PGPASSWORD -- psql -h db -U app

sec render

Fill a template file with secrets → a 0600 output file; the placement is recorded, so rotate re-renders it.

sec render TEMPLATE --out FILE

sec render conf.tmpl --out conf.yaml
✓ rendered conf.tmpl → conf.yaml (0600; 2 secret(s), placement recorded)

sec env

Dotenv files without reading them. To write a value into one: sec push NAME .env [--as VAR].

sec env ls TARGET                   # the keys in a dotenv (names only)
sec env list

sec seal

The reverse of render: puts {{NAME}} back where a file holds real values. Commit the sealed file; render puts the values back.

sec seal FILE [--out FILE] [--check]

sec seal config.yaml
sec seal notes.md --check     # only report; exit 1 if a live value is found

sec get

sec get NAME --out FILE   # raw value to a NEW 0600 file, never stdout (agents ok; existing file/symlink refused)
sec get NAME --print      # owner-only, and denied at the harness for agents

5 · Store — put secrets in the vault

sec set

Store a value from stdin — a masked prompt on a TTY, raw stdin from a pipe or heredoc. The value never touches argv.

sec set NAME [--source URL] [--raw] [--place]  < value on stdin
sec set NAME --from FILE|DIR

  --source URL|note   where this is minted/revoked — used by rotate
  --raw               keep the trailing newline (PEM / JSON material)
  --place             after storing, re-apply to every recorded placement
  --from FILE|DIR     store a whole file or folder instead of a value

printf '%s' "$VALUE" | sec set STRIPE_KEY --source https://dashboard.stripe.com/apikeys
sec set TLS --from ./certs
✓ TLS stored (v1, folder of 3 entries, 1824 bytes)

If the value arrived through an agent, sec says so and suggests rotating once the real source can mint a fresh one. On a TTY the prompt echoes * per key; a paste shows only its last 3 characters plus a count — *********XYZ (12 chars) — so you can check the key; typing hides them again. Long values cap at 32 stars.

--from takes a cert, a key file or a folder. A folder is one encrypted archive of its regular files and directories with permission bits; symlinks, sockets and devices are skipped and listed. The source path is not recorded as a destination — sec never writes back over your original. Put it somewhere with sec push.

sec gen

Generate a password or token straight into the vault and/or a dotenv. Never displayed.

sec gen --save NAME [--len 32] [--hex] [--no-symbols] [--env FILE=VAR]

  --save NAME      store as this secret
  --len N          length in chars, or bytes with --hex (default 32)
  --hex            hex token of --len random bytes
  --no-symbols     letters and digits only
  --env FILE=VAR   also write to a dotenv file (repeatable via comma)
  --print          owner-only: print instead

sec gen --save DB_PW --env .env=DB_PASSWORD
sec gen --save SESSION_KEY --hex --len 32

sec import

Import every KEY=value of a dotenv. The file itself becomes a placement, so a later rotate updates it.

sec import FILE|ENV [--project P] [--env E] [--only A,B] [--no-place]
sec import SEALED_FILE        # from sec export --for
sec import -                  # sealed export on stdin (what sec sync runs)

sec import .env.production --project reqsume --env production
sec import production --only DB_PW,API_KEY
sec import x.sec

The target is any existing file whatever its name, or an environment name resolved to its dotenv. A sealed export is recognised by its header and opened with this vault's key; one sealed for a different key is refused.

sec ls · sec rm

sec ls [--project P] [--env E] [--json]   # names, version, placements, last use — never values
sec rm NAME            # delete a secret and its retired versions; placed copies are NOT removed

sec use · sec project

sec use                          # show the current context and where it comes from
sec use PROJECT [--env E]        # set it (saved in SEC_HOME/context.json)
sec use --env E                  # env only
sec use --unset | --reset        # back to the global namespace
sec project ls [--json]          # projects, environments, secret counts

6 · Move — between machines

Which verb? (sec help move)

SituationVerbExample
You can reach it (ssh / docker / k8s) and it runs secsec syncsec sync DB_PW,API_KEY ssh://deploy@db
A program there reads a file / .env / folder, not a vaultsec pushsec push TLS ssh://web/etc/app/certs
No connection at all (air gap, email, USB)sec export --for + sec importsec export --only DB_PW --for age1… --out x.sec
Put sec itself there, or bring it to this version (no secrets move)sec remotesec remote upgrade ssh://db
A plaintext .env for a tool that needs onesec export --confirm (owner)sec export --only DB_PW --out prod.env --confirm

Agents may sync to a pinned/saved target, push to recorded places and import. The owner does first-contact sync, --install, --repin, the first push elsewhere, export, and remote install/upgrade/uninstall; --purge only at a real terminal.

sec sync

Move secrets into (or out of) another sec in one step. The remote key is fetched, values are sealed for it in memory and streamed into sec import - there: no temp file on either side, only names and versions printed.

sec sync NAME[,NAME] WHERE [--dry] [--install] [--repin] [--remote-sec PATH]
sec sync NAME[,NAME] --from WHERE [--dry]

sec sync DB_PW,API_KEY ssh://deploy@db.example.com
sec sync DB_PW docker://api --install       # no sec there yet: streams it (no admin, any OS)
sec sync DB_PW k8s://prod/api-7d9f/app
sec sync DB_PW --from ssh://db --dry        # names + remote key fingerprint, sends nothing

Routes and + chains

ssh://[user@]host[:port]               ssh host CMD
docker://ctr    podman://ctr           docker exec -i ctr CMD
k8s://pod  k8s://ns/pod[/container]    k8s://context/ns/pod/[container]
ssh://web+docker://api                 ssh in, then into a container (+podman://, +k8s://)
ssh://bastion+ssh://db                 through a jump host
ssh://bastion+ssh://db+k8s://ns/pod    through a jump host, into a pod
db                                     a saved target
  • The remote key is pinned per target on first contact. An agent may sync only to a pinned key or one the owner saved with sec target add NAME age1…; first contact, --install and --repin are owner-only. A pinned target whose key changed is refused.
  • --install detects the far end (uname -sm, or PowerShell on Windows), streams a matching, checksum-verified sec into that user's own folder — ~/.local/bin or %LOCALAPPDATA%\Programs\sec — never root, and runs sec init.
  • Both sides write the audit log.

sec push

Put secrets where a program already reads them, and remember it — so rotate, set --place and ok keep that copy current. Programs never call sec.

sec push NAME[,NAME] WHERE [--as NEW] [--mode 0600] [--once]
sec push NAME -- CMD-ON-THE-OTHER-END [--path P]

WHERE
  ./app/.env                     KEY=value line(s) in a dotenv; other lines untouched
  ./certs   /srv/vol/tls.key     the value / file / folder, written whole
  ssh://[user@]host[:port]/path  a file / folder on a server — needs only sh + tar there
  ssh://host                     into that server's own sec vault
  ssh://web+docker://api/path    same + chains as sync; the path is on the last hop
  docker://ctr/path              inside a running container   (also podman://)
  k8s://pod/path                 inside a pod, via kubectl exec
  gh://owner/repo[:env]          a GitHub Actions secret, repo or environment level (via gh)
  gcp://project                  a GCP Secret Manager secret (via gcloud)
  prod                           a saved target

  --as NEW          name / variable on the other end (one secret only)
  --mode 0640       file mode when writing a file (default 0600)
  --once            push now, don't remember it
  --remote-sec P    sec binary on the other end (non-login ssh may need ~/.local/bin/sec)

sec push DB_PW,API_KEY ./app/.env
sec push DB_PW .env.production --as DATABASE_PASSWORD
sec push GH_TOKEN gh://muthu/app:prod
sec push TLS ssh://deploy@hetzner/etc/myapp/certs
sec push DB_PW docker://api/run/secrets/db_pw
sec push TLS --path /etc/x -- kubectl exec -i pod/api --     # escape hatch
  • The value travels on stdin — never argv, never a temp file on either side.
  • Files are written to a temp name and renamed; a folder is unpacked beside the old one and swapped in, so a reader never sees half a write.
  • A first push to another machine is owner-only; re-pushes to recorded places (rotate, set --place, ok) are not.
  • A path takes one file/folder secret; several values go into a .env path. Editing one line of a remote .env is not supported — push the whole file.
  • Every push is a place.apply line in the log.

sec target

Save a destination once; use its name in push/sync, or a sec key in export --for.

sec target add NAME URL|age1…
sec target ls
sec target rm NAME

sec target add db ssh://deploy@db
sec target add db-key age1…      # pins that key: agents may now sync

sec remote

Put sec on another machine, container or pod (any sync route), or bring it to this version. No secrets move; never root, sudo or Administrator. Owner-only except status.

sec remote status WHERE                      # its version vs this one, vault y/n
sec remote install WHERE [--dry]
sec remote upgrade WHERE [--dry]             # keeps sec.prev; rolls back on failure or name-count change
sec remote uninstall WHERE [--dry]           # keeps its vault
sec remote uninstall WHERE --purge [--force] # owner at a real terminal; --force for secrets only there

sec remote install|upgrade and sec sync --install also install the agent skill on the far end (--no-skill skips it).

sec export · import

Owner-only (and denied to Claude by Bash(sec export:*)). Names go in --only, never as positionals.

sec export --out FILE --for KEY|TARGET [--only A,B]   # sealed: only that vault can open it
sec export --out FILE --confirm [--only A,B]          # PLAINTEXT .env (0600)

there:  sec id                                        # → age1…
here:   sec export --only DB_PW,TLS --for age1… --out x.sec
there:  sec import x.sec

A sealed export is a one-off copy: after a rotate, export again. If you can reach the machine, sec sync does it in one step.

sec id

Print this vault's public key (age1…) — what a sender passes to sec export --for or sec target add NAME <key>.

sec hub — a team's secrets on one ssh server

One server you run, reachable over ssh only. Login is an ssh key; each user has read or write per project (optionally per env); the first user is admin. Values are encrypted at rest with the server's own key — not blind: you run it, you trust it. The hub is never named in the repo: sec login keeps it in your sec home. The client uses your system ssh, so the agent, ~/.ssh/config and known_hosts just work.

sec hub serve --data /srv/sec-hub --listen :2222 --admin alice=alice.pub   # on the server
sec login ssh://hub.example.com:2222           # once per machine; kept in your sec home, not the repo
sec load                                       # this repo's project@env (team copy) → .env
$EDITOR .env && sec save                       # changes → vault → hub (merged, nobody's keys dropped)
sec add config/sa.json certs/              # files/folders too: sec load puts them back
sec login https://hub.example.com          # hub over https works the same
sec hub pull [ENV]                             # hub → project@env in the local vault
sec hub push [ENV]                             # local project@env → hub (replaces that env; old copy kept)
sec hub user add NAME KEY.pub --role read|write --project P [--env E]
sec hub user rm NAME  ·  sec hub user ls  ·  sec hub log [-n N]  ·  sec logs --hub

CI: make a key, sec hub user add ci ci.pub --role read --project P --env production, put the private key in SEC_HUB_KEY and set SEC_ENV. sec run / sec exec then pull that env into memory — no sec init, nothing on disk. hub push and hub user add/rm are owner-only. The hub's log (log.jsonl) holds names, never values.

7 · Audit & rotate

sec where

Every placement plus recent uses of a secret — the compromise-day question.

sec where DB_PW

sec logs

The audit log, newest last, every field shown; failures marked ✗.

sec logs [NAME | --name NAME] [--since 7d] [--action A] [-n 50] [--json]
sec logs --retired     # old versions still to revoke upstream

sec logs DB_PW --since 7d
sec logs --action sync.push

sec keys

Which keys a project needs are in the vault, and which are missing. With no arguments it reads .env.example / .env.sample / .env.template / *.tmpl in the current directory. {{NAME}} placeholders count, otherwise dotenv keys. Exits 1 if anything is missing.

sec keys [FILE…]
.env.example  (3 keys)
  ✓ DB_PW
  ✓ API_KEY
  ✗ STRIPE_KEY   missing — sec set STRIPE_KEY

sec ok

The one command to run when unsure. Fixes what is provably safe and lists the rest with the command to run.

sec ok [--dry] [-v]

✓ vault unlocked, 14 secret(s), key in keyring
✗ STRIPE_KEY missing (needed by .env.example)   → sec set STRIPE_KEY
↻ DB_PW → file   /srv/myapp/.env  (DB_PW): has v2, vault has v3 → re-pushed ✓
⚠ API_KEY v1 replaced 12 days ago — revoke it at its source, then   → sec rotate API_KEY --purge
  • Fixes: a copy the log shows holds an older version — re-pushed.
  • Never touches: a destination with no version on record, a file that was deleted, and relative-path placements recorded by an older sec.
  • Reports: missing keys, replaced versions older than 7 days still to revoke, whether the agent hook is installed. Exit 1 when something needs you.

sec rotate

New value → re-pushed to every recorded placement → the steps it cannot do are printed.

sec rotate NAME [--gen | < new value] [--hook SCRIPT]
sec rotate NAME --undo | --purge

  --gen            generate the new value here (passwords you own, e.g. DB users)
  --len N          length for --gen (default 32)
  --no-symbols     for --gen
  --hook SCRIPT    run with SEC_NAME / SEC_NEW_VALUE / SEC_OLD_VALUE set, to apply it at the source
  --undo           bring back the previous version and re-place it
  --purge          drop retired ciphertexts, after you revoked them upstream

sec rotate DB_PW --gen --hook ./alter-user.sh

The old version stays listed as "still to revoke upstream" until --purge: sec will not mark a revocation done that it did not witness.

8 · Agents

The skill · sec skill install

The skill is built into the binary: SKILL.md is the index (the one rule: write {{NAME}}, hand it to sec), with detail in references/ — commands.md, moving.md, permissions.md, projects-and-envs.md, identity-and-agent.md, scenarios.md.

sec skill install [--no-settings]          # write the built-in skill + deny rules
sec skill install --from ./skills/sec      # symlink a checkout instead (development)
  • Written to ~/.claude/skills/sec, ~/.agents/skills/sec and $CLAUDE_CONFIG_DIR/skills/sec when that is set.
  • Auto-install: the first sec run on a machine installs it (see bare binary). Auto-refresh: every run rewrites a sec-written copy that is out of date.
  • --no-settings skips the deny rules.

Harness deny rules

Merged into each Claude settings.json permissions.deny, so the harness refuses — not the model:

Read(~/.config/sec/**)     # the vault and the identity
Read(**/.env)              # the files sec writes for you
Read(**/.env.*)
Bash(sec get:*)            # the print path
Bash(sec export:*)         # the bulk print path

sec agent

Run an agent with the human's keyboard going through sec first: every paste and Enter is checked for secrets; one found is stored in the vault and the agent gets {{NAME}}. The agent's shell becomes sec sh (the agent-shell mode of exec), and for claude the hook is wired in for the session. Arguments after the agent name pass through untouched. Without a working vault it will not start.

sec agent AGENT [agent args…]

sec agent claude
sec agent codex

sec hook

Pre-tool guard: an agent's file reads, writes and searches (Bash, Read, Write, Edit, Grep, Glob, notebooks) go past sec first; a denied call is audited as hook.deny. sec agent claude wires it in for that session; sec skill install does not.

sec hook --client claude

sec sh

The agent's shell: refuses reads of secret files, fills {{NAME}}, redacts all output. sec agent sets it as SHELL / CLAUDE_CODE_SHELL.

sec sh [shell args]

9 · CI / read-only vaults

With SEC_READONLY=1 a vault can be used but never changed: only ls run exec render seal keys where logs env id use project run; every other command is refused, including writes through the Go package, and the skill auto-install/refresh is skipped. Use sec init --backend file on a CI runner.

SEC_READONLY=1 sec run DB_URL,API_TOKEN -- npm run e2e

10 · Go package — pkg/vault

github.com/muthuishere/sec/pkg/vault opens the same vault from a Go program. No export path; every read is audited with the caller's label.

v, _ := vault.OpenAs("myapp")
token, _ := v.Get("API_TOKEN")      // pass straight to a client, never print
names, _ := v.List()
clean := vault.Redact(out, map[string]string{"API_TOKEN": token})

12 · Threat model

sec defends against sloppiness and logs — secrets in transcripts, guides, commits, test output, chat. It does not defend against a hostile agent with network access: it could curl a value to a webhook through exec, and so could every other tool in this category. The refusal of output-only commands and the audit line for every use make the silly attempt visible, not impossible.

sec identity

sec identity [show [--json]]               # which backend holds the key
sec identity move --to keyring|file        # verifies the new location reads back BEFORE removing the old
sec identity export --out FILE --confirm   # a backup for your password manager
sec identity import FILE [--backend keyring|file]
sec identity adopt KEY_FILE

What the keyring buys you: no plaintext key on disk, so a disk image, a backup or an rclone of the wrong directory doesn't carry it. What it does not buy you: it cannot stop a process running as you from asking the keyring — identical exposure to a 0600 file.
