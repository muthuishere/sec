one static Go binary · no daemon · no SaaS

Your agent uses the key.
It never sees the key.

Coding agents need credentials and are the worst possible place to put one — every value they touch lands in a transcript, a prompt cache, a log, a commit. sec hands the agent a placeholder instead. It fills {{NAME}} at the moment of execution, in a child process, and scrubs the value back out of everything that comes home.

$ curl -fsSL https://raw.githubusercontent.com/muthuishere/sec/main/install.sh | sh
> curl.exe -fsSL https://raw.githubusercontent.com/muthuishere/sec/main/install.cmd -o "%TEMP%\sec-install.cmd" && "%TEMP%\sec-install.cmd"

Puts sec on your PATH and installs the agent skill into ~/.claude/skills and ~/.agents/skills. Downloaded a bare binary instead? It installs the skill on its first run, and any later run keeps it current. Re-run the line to upgrade. Building from source works too.

60-second quickstart Watch the 4-minute demo
60 seconds

Init, store, use. Then hand it to your agent.

first run
# 1. create the age identity + an empty vault (key goes in the OS keyring;
#    on servers/CI: sec init --backend file)
$ sec init

# 2. store a value — masked prompt, never argv, never shell history
$ sec set GH_TOKEN

# 3. use it by name; sec fills {{GH_TOKEN}} in a child process
$ sec exec -- sh -c 'curl -sS -H "Authorization: Bearer {{GH_TOKEN}}" https://api.github.com/user | head -3; echo "sent {{GH_TOKEN}}"'
{
  "login": "you",
  "id": 1234567,
sent [REDACTED:GH_TOKEN]

# already have a .env? bring every KEY=value in at once
$ sec import .env

Now ask your agent. "List my GitHub repos." "Run the integration tests against staging." The installed skill teaches it to write {{NAME}} and call sec; it finds names with sec ls --json and never gets a value back. If a key is missing, sec keys .env.example says which.

One unbroken Claude Haiku 4.5 session against a throwaway vault. Every command in this film was issued by the agent, not typed by a human. It leaks the key doing an ordinary job, gets stopped by the harness, then does the same work through sec — generating, rendering, tracking, rotating and auditing a credential it is never allowed to see — and finally tries to get the value back out through base64, a hex dump and fold -w 12, and can't.

a real session — output below is copied verbatim
# the agent writes this. It has never read STRIPE_KEY and cannot.
$ sec exec -- sh -c 'echo "key is {{STRIPE_KEY}}"'
key is [REDACTED:STRIPE_KEY]

# same for env-var injection
$ sec run STRIPE_KEY -- sh -c 'echo "env: $STRIPE_KEY"'
env: [REDACTED:STRIPE_KEY]

# the value re-encoded on the way out
$ sec exec -- sh -c 'printf %s {{STRIPE_KEY}} | base64'
[REDACTED:STRIPE_KEY]

# and re-encoded *and* wrapped — one character per line, the worst case
$ sec exec -- sh -c 'printf %s {{STRIPE_KEY}} | fold -w 1'
[REDACTED:STRIPE_KEY]

The real key went to the child process. What came back to the model is a label. Redaction covers the raw value and its base64 (with and without trailing newline), hex, URL-encoded and JSON-escaped forms — because a leak rarely comes out in the shape it went in. Matching is newline-tolerant: ordinary tools wrap long output — xxd -p at 60 columns, GNU base64 at 76, fold wherever you ask — and a value that comes back in three pieces is still the value, so the stream is searched with the line breaks removed too.

the problem

A secret doesn't leak once. It leaks everywhere it was copied.

The agent era didn't invent credential sprawl. It industrialised it — a value pasted into a prompt is now in a transcript, a cache, a summary and three files nobody kept track of.

without sec

The value is in the conversation

You paste the key so the agent can test the endpoint. It's now in the request body, the response, the session log on disk, the commit the agent made "to save progress", and the summary it wrote when the context compacted. You can't un-paste it — you can only rotate it, and you don't know everywhere it went.

~/.claude/projects/…/session.jsonl   ← it's in here
git log -p                            ← and here
.env.dev, conf.yaml, CI, the ticket   ← and here
with sec

The value is in a child process, for 40ms

The agent writes {{STRIPE_KEY}}. sec decrypts, substitutes, execs, scrubs stdout and stderr line by line, and writes one audit line naming the secret — never the value. The harness itself refuses sec get, so the refusal isn't the model's good behaviour, it's a deny rule the model cannot argue with.

transcript   [REDACTED:STRIPE_KEY]
audit.ndjson exec STRIPE_KEY claude-code
vault        STRIPE_KEY.age (ciphertext)
the harness, not the model

Four layers, so the agent never has to be trustworthy.

the skillA short SKILL.md index plus references/*.md — commands, moving secrets, projects & envs, permissions, identity, and scenarios (worked tasks like "the key leaked", "set up the .env", "copy secrets to the server"). The agent loads only the page it needs.
auto-refreshThe skill is built into the binary. sec skill install writes that copy; every later sec run rewrites it when a new sec ships, so the instructions never drift from the CLI. (--from DIR symlinks a checkout for development.)
sec agentsec agent claude (or codex, devin, …) runs the agent with every paste and Enter checked for secrets before the agent sees it, its shell set to sec sh, and — for Claude — sec hook wired in for that session.
sec shThe agent-shell mode of sec exec, set by sec agent: refuses reads of secret files, fills {{NAME}}, and redacts all output — so even a plain cat .env comes back empty-handed.
sec hookA Claude Code PreToolUse guard on Bash, Read, Write, Edit, Grep, Glob and notebooks: a file that holds vault values is denied before the tool runs, and the denial is an audit line.
deny rulessec skill install merges these into ~/.claude/settings.json (skip with --no-settings).
~/.claude/settings.json → permissions.deny
  Read(~/.config/sec/**)     # the vault and the identity
  Read(**/.env)              # the files sec writes for you
  Read(**/.env.*)
  Bash(sec get:*)            # the print path
  Bash(sec export:*)         # the bulk print path

The same shape AWS now recommends for agents — a harness-level rule that blocks the read-the-value call outright — but for any credential, not one cloud's. On top sits the owner check: a TTY on stdin (or SEC_OWNER=1) is the owner; agent harnesses run with piped stdin, so get --print and export fail by construction, not by persuasion.

past the env var

Most brokers can only fill an environment variable.
Half of real config isn't one.

A TLS key in a YAML file. A token in a CLI argument. A service-account JSON a tool reads by path. exec and render cover the shapes an env-only doppler run structurally cannot.

verbatim session
$ cat conf.tmpl
db:
  password: {{APP_DB_PW}}
  stripe: {{STRIPE_KEY}}

$ sec render conf.tmpl --out conf.yaml
✓ rendered conf.tmpl → conf.yaml (0600; 2 secret(s), placement recorded)

$ sec gen --save APP_DB_PW --len 32 --env .env.dev=DB_PASSWORD
✓ DB_PASSWORD written to .env.dev (0600)
✓ APP_DB_PW stored (v1, 32 chars)

The generated password was never printed, never in argv, never in the agent's context — and the output file is 0600. "placement recorded" is the part that pays off next.

past the laptop

Put it where the program already looks.

Programs never call sec. sec push writes a value — or a whole cert file, or a folder — where the program reads it. sec sync moves secrets into another sec's vault, sealed for its key. Both are remembered, so the next rotate updates every copy.

push · sync · remote
# push: plain files where programs read them
$ sec set TLS --from ./certs
✓ TLS stored (v1, folder of 3 entries, 1824 bytes)
$ sec push DB_PW,API_KEY ./app/.env
$ sec push TLS ssh://web/etc/app/certs       # needs only sh + tar there
$ sec push DB_PW docker://api/run/secrets/db_pw

# sync: into the other machine's own sec vault — ssh, docker, podman, k8s, chained with +
$ sec sync DB_PW,API_KEY ssh://deploy@db.example.com
$ sec sync DB_PW docker://api --install
$ sec sync DB_PW k8s://prod/api-7d9f/app
$ sec sync DB_PW ssh://web+docker://api      # ssh in, then into a container (also podman://, k8s://)
$ sec sync DB_PW --from ssh://db --dry

# remote: put sec itself there, or bring it to this version (no secrets move)
$ sec remote status ssh://db
$ sec remote upgrade ssh://db --dry

The value travels on stdin — never argv, never a temp file. Files are written to a temp name and renamed; folders are unpacked beside the old one and swapped in, permissions kept. A first push or sync to a new machine is owner-only: an agent cannot pick a new destination, but re-pushes to the ones you set up happen on every rotate, and agents may sync to a target whose key is already pinned (sec target add). No ssh at all? sec export --for <its sec id> makes a sealed file only that vault can sec import. remote upgrade keeps the previous binary and rolls back if the new one fails.

the compromise-day question

"Where did this key end up?" should be one command, not an afternoon.

Every write — push, render, import, gen --env — records a placement. Rotation replays the ledger instead of asking you to remember it, and prints the steps a tool honestly cannot do for you.

verbatim session
$ sec rotate APP_DB_PW --gen
✓ APP_DB_PW v1 → v2
  ✓ file   .env.dev  (DB_PASSWORD)
  ✓ render conf.yaml  <- conf.tmpl

MANUAL steps:
  ⚠ the generated value was NOT applied at the source (no --hook) — apply it there, or `sec rotate APP_DB_PW --undo`
  ⚠ restart whatever reads .env.dev
  ⚠ restart whatever reads conf.yaml
  · when the old value is revoked: sec rotate APP_DB_PW --purge

$ sec where APP_DB_PW
APP_DB_PW  v2  updated 2026-09-19 13:38
placements (2):
  file   .env.dev  (DB_PASSWORD)   [2026-09-19]
  render conf.yaml  <- conf.tmpl   [2026-09-19]
retired versions still to revoke upstream: v1(09-19)   → `sec logs --retired`, then `sec rotate NAME --purge` once revoked
activity in the last 30 days (3):
  09-19 19:08  rotate    claude-code
  09-19 19:08  render    claude-code
  09-19 19:08  gen       claude-code

Give it --hook hooks/postgres-rotate.sh and the source is rotated too — the hook receives SEC_NAME, SEC_NEW_VALUE and SEC_OLD_VALUE in its environment, so the value never reaches argv. hooks/ ships Postgres and AWS IAM to copy. Note what it refuses to claim: an old version stays listed as "still to revoke upstream" until you tell it the revocation actually happened.

one command when unsure

sec ok

sec ok
✓ vault unlocked, 14 secret(s), key in keyring
✗ STRIPE_KEY missing (needed by .env.example)   → sec set STRIPE_KEY
↻ DB_PW → file   /srv/myapp/.env  (DB_PW): has v2, vault has v3 → re-pushed ✓
✓ 9 placement(s) hold the current version
⚠ API_KEY v1 replaced 12 days ago — revoke it at its source, then   → sec rotate API_KEY --purge

It fixes only what it can prove: a copy that exists and holds an older version. It will not push anywhere it has no version on record, will not recreate a file you deleted, and lists everything else with the exact command to run. --dry changes nothing. sec keys answers "what is this project missing"; sec logs answers "what happened".

Secrets can be scoped to a project and an environment — myapp@prod:DB_PW vs myapp@dev:DB_PW — with sec use myapp --env prod setting the default.

how it works

Three moving parts, none of them a server.

01

An age-encrypted vault

~/.config/sec/vault/NAME.age — X25519 via filippo.io/age, plus a NAME.json of metadata. Ciphertext and names only, so the directory is safe to commit to a private repo or rclone sync. Sync is deliberately not sec's job.

02

A pluggable identity

The same three backends Bun.secrets gives JS, plus a file: SEC_IDENTITY (CI) > OS keyring > identity.txt (0400). macOS and Windows default to the keyring; Linux defaults to the file, because a server has no Secret Service and a desktop one is DBus that can block forever on a prompt nobody is there to answer.

03

An owner check with no model in it

A TTY on stdin — or an explicit SEC_OWNER=1 — is the owner. Agent harnesses run with a piped stdin, so they never have it. get --print, export and every output-only path fail by construction, not by persuasion.

the surface

Thirty-six commands. You will use eight.

sec setStore a value from stdin — masked prompt on a TTY, never argv.
sec execRun a command or script with {{NAME}} placeholders filled; output scrubbed.
sec runRun a command with NAME injected as an env var; output scrubbed.
sec genMint a password or token straight into the vault and a .env — never displayed.
sec whereEvery placement and recent use of a secret. The compromise-day question.
sec pushPut values, files or folders where a program reads them — .env, volume, ssh://, docker:// — and remember it.
sec okCheck everything; re-push stale copies, list what needs you.
sec rotateNew value → re-pushed to every placement → manual steps listed honestly.

The rest — init · ls · get · rm · use · project · import · env · render · seal · agent · export · id · sync · remote · target · logs · keys · hook · identity · skill — are in the docs, and sec help <command> prints the syntax with examples. Local TLS: make the certs with mkcert, then sec set TLS --from ./certs keeps the keys in the vault instead of world-readable in /tmp.

threat model, honestly

What this does not defend against.

sec defends against sloppiness and logs — secrets in transcripts, guides, commits, test output, screen-shares, chat.

It does not defend against a hostile agent with network access. Such an agent could curl a value to a webhook through exec — and so could every other tool in this category, including the ones that don't say so. What sec adds is that the silly attempt is visible: an audit line names the secret, the command and the agent. Visible, not impossible. Anyone promising otherwise is selling you a proxy and a dashboard.
